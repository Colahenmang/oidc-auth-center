# 完整的项目提示词与上下文

我参考 Authing 的托管登录流程，使用 Codex 实现了一个 OIDC 员工认证中心。工单、人事和财务共用认证中心，各自维护应用会话。管理员可以登记应用、修改回调地址和管理人事访问权限。

下面的复现提示词按八个阶段写，每一步接着上一步的结果往下做。确认做什么以后，我会让 Codex 给出能自己操作的检查步骤，再用浏览器看效果。实际做过的检查见[实际验收结果](#实际验收结果)和[对应的 Git 提交](#验收与-git-提交)。

## 项目上下文

- 开发一个基于 OIDC 的员工认证中心，为接入的应用提供统一登录，支持配置登录回调地址。以 Authing 的托管登录流程作为交互参考。
- 项目包括认证中心、预置的工单和人事应用，以及通过界面登记后启动的财务演示。管理员可以登记应用、分别修改已登记应用的回调地址，在员工管理页创建和搜索员工，并逐人管理人事访问权限。
- 开发环境为 Windows、Java 21 和 Maven，使用 Spring Boot 4.0.9、Spring Security 和服务端模板。认证中心、工单、人事和财务分别在 `9000`、`8081`、`8082`、`8083` 运行。

## Authing 产品参考

我先在 Authing 控制台创建用户池和标准 Web 应用，配置登录回调 URL，再点「体验登录」。认证成功后，浏览器跳到配置的演示回调页，地址中带有授权码。这个操作让我明确了认证中心、接入应用和回调地址分别承担什么职责。[Authing 托管登录体验](https://docs.authing.cn/v2/guides/basics/authenticate-first-user/use-hosted-login-page.html)

界面参考了 Authing 将应用列表、配置入口和托管登录页分开的做法。项目首页集中展示三个演示入口，管理员从同一控制台登记应用、修改回调和管理员工，员工从业务应用进入统一登录表单。[Authing 自建应用](https://docs.authing.cn/v2/concepts/application.html)

| 在 Authing 看到的流程 | 在项目中怎么体现 |
| --- | --- |
| 应用先登记，再设置可回跳的 URL | 管理员从应用配置登记财务应用，获取应用 ID 和密钥，并为每个应用分别管理回调。授权请求必须匹配对应应用登记的完整地址。 |
| 用户在认证中心页面输入凭证 | 工单、人事和财务共用认证中心的员工目录。已登录的员工打开另一个接入应用时，可复用认证中心会话。 |
| 登录成功后浏览器带授权码跳回应用 | 工单后端接收并兑换授权码，验证身份后页面显示当前员工，刷新时使用工单自己的会话。 |
| 应用可以限制哪些用户能进入 | 管理员从员工目录逐人开通或取消人事权限；工单继续作为员工登录的基础入口。 |

## 复现提示词

### 1. 明确需求和技术方案

> 我在 Authing 里试了一遍，应用先登记回调地址，登录完浏览器再跳回去。我现在想用 Java 做一个小版，先让工单接进来。你帮我看下 Spring Security 官方示例，讲明白认证中心和工单各负责哪一段。先给我个能跑起来的方案，告诉我每一步做完在哪儿点、看到什么算通过。

这一步要能说清楚登录前从哪出发、账号密码在哪填、登录后回哪儿。先做工单登录，等它跑通了再做管理页。

### 2. 实现并验收登录闭环

> 就按你说的先跑工单。工单和认证中心各自启动，我在工单点登录，去认证中心输账号密码，再回到工单看到自己是谁。OIDC 这段用 Spring Security，工单后端拿授权码去换并校验 ID Token。弄好后把启动命令、入口和测试账号给我，我自己走一遍。

输错密码时停在登录流程。正确登录后工单显示「小朱」和员工 ID，刷新页面还能看到登录状态。

### 3. 增加回调地址配置

> 登录通了以后，再加个管理员页面，我想自己进去改工单的回调地址。改的值存进 H2。认证中心按登记的完整地址检查，端口或者路径换了也要算不匹配。我想先只改管理页看它怎么报错，再把工单那边也改对，看能不能重新登录。

普通员工进不了管理页。管理员保存新回调后，工单用旧地址登录收到 `400`，两边改一致后能登录。重启认证中心再看保存的配置是否还在。

### 4. 对照浏览器请求和源码验收

> 我在 Network 里看到好几条 `302`，有点分不清哪条是回调。你告诉我该点哪条、在哪看 `Location`，还有怎么确认刷新后工单记得我。也带我对一下代码，回调在哪检查，授权码在哪儿换，工单页又是从哪儿拿到员工名字的。

先找 `Location` 和带 `code=` 的回调请求，再看回调响应的 `Set-Cookie` 和刷新后的 `Cookie`。将这几条请求对应到项目代码和 Spring Security 的处理。

### 5. 打磨演示页面和容器启动方式

> 现在流程能走了。页面上帮我把登录成功、回调保存、地址填错和没权限这几种情况显示清楚。Java 本地启动的步骤留着，再加一份 Docker Compose 配置。浏览器进去的地址和容器互相访问的地址可能不同，这两边怎么填也说明一下。

本地用浏览器检查正常和失败的反馈，另外校验 Compose 配置。实际完成到哪一步写进 README。

### 6. 用第二个应用验证单点登录和权限

> 一个工单看不出单点登录，再加个人事试一下。先让我能分别改工单和人事的回调。接着我用小朱登工单，在同一个浏览器再点人事，看看还用不用输密码。最后加个员工列表，能新建和搜索员工，也能单独关掉某个人的人事权限。每做完一段就告诉我怎么点。

改人事回调时工单的值不变。工单登录后，人事可免输密码。取消小朱的人事权限后退出人事并重新登录，确认人事拒绝、工单仍能登录，再重新开通人事验证恢复。

### 7. 通过界面登记并接入财务应用

> 我想看看临时加一个系统能不能接进来。你在管理页加个「新增应用」，我填个财务和它的回调地址。应用 ID 和密钥由后端生成，密钥明文就创建成功时给我看一次，后端存哈希。财务用 `finance` 配置跑在 `8083`，我用环境变量把刚生成的凭据传进去。你把顺序告诉我，我按步骤从登记做到登录。

用新凭据启动财务，确认登录后回到财务页并显示员工身份。刷新登记页确认明文密钥已隐藏，换财务回调再检查旧地址会被拒绝。

### 8. 完善认证中心前端与演示体验

> 到这一步我想把页面再收拾一下。我看 Authing 的应用列表和登录页挺好找的，我们也让新增应用、改回调和管权限这几个入口容易找到。窄一点的屏幕也试下，尤其是很长的回调地址。改完再用员工和管理员各走一遍。

用桌面和窄屏看表单与提示，重新检查登录回跳、回调错误和人事权限。

## 参考项目及用法

- 用 Spring Security 7.0 的官方入门对照认证中心的 OIDC 开关、协议端点、安全链、客户端登记和签名密钥。[Spring 授权服务器入门](https://docs.spring.io/spring-security/reference/7.0/servlet/oauth2/authorization-server/getting-started.html)
- 对照 Spring 官方示例里的服务端与客户端，看两边如何对应应用 ID、issuer 和回调。示例与本项目的依赖版本不同，类名和配置项以 7.0 文档和实际依赖为准。[官方授权服务示例](https://github.com/spring-attic/spring-authorization-server/blob/1.5.x/samples/demo-authorizationserver/src/main/java/sample/config/AuthorizationServerConfig.java) · [官方配套客户端](https://github.com/spring-attic/spring-authorization-server/blob/1.5.x/samples/demo-client/src/main/resources/application.yml)
- 工单端用 Spring Security 自带的授权码登录，自己实现的页面从服务端已验证的 OIDC 用户信息读取姓名和员工 ID。[Spring OIDC 客户端说明](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/)
- 认证中心沿用 Spring 的客户端登记模型。管理员修改数据库里的回调地址后，授权端点执行精确匹配。Spring 的默认 loopback 校验有端口例外，本演示的 Web 客户端把端口也纳入精确匹配。[Spring 回调校验扩展示例](https://docs.spring.io/spring-security/reference/7.0/servlet/oauth2/authorization-server/protocol-endpoints.html#oauth2-authorization-endpoint)
- 使用多阶段镜像构建两个 Java 模块。Compose 用 OIDC 发现端点检查认证中心是否就绪，并让工单后端通过服务名访问认证中心。[Docker 多阶段构建](https://docs.docker.com/get-started/docker-concepts/building-images/multi-stage-builds/) · [Compose 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/) · [Spring 客户端登记配置](https://docs.spring.io/spring-security/reference/7.0/servlet/oauth2/client/core.html#oauth2Client-client-registration)

## 实际验收结果

**我在浏览器里验证的步骤**

我用管理员账号保存回调地址，并在 Network 里看到配置表单提交了 `redirectUri`。我把回调恢复到默认的 `8081`，从工单页再次发起登录，看到认证中心返回 `302`，浏览器随后访问 `8081/login/oauth2/code/work-order?code=…`。工单回调响应里有 `Set-Cookie: DEMO_SESSION=…`，刷新工单首页的请求里则带有 `Cookie: DEMO_SESSION=…`。那次浏览器沿用了管理员身份，工单页显示 `admin`，与当前登录身份一致。通过这次观察，我把回调地址检查、身份凭证兑换和工单会话分别对应到了认证中心、Spring Security 客户端和工单首页代码。

我把人事回调改成 `/hr-alternate` 后刷新，确认设置保留、工单回调没有变化，再把人事改回 `/hr`。随后用小朱登录工单，再登录人事，确认只输了一次密码、两个页面都显示小朱。我也验证了小朱被取消人事权限后仍能登录工单，重新开通后又能登录人事。

我在应用配置页登记了财务演示，并在 Codex 启动财务后端后用浏览器验证了登录回跳。

**Codex 联调验证的步骤**

- Maven 构建通过。PowerShell 联调覆盖错误密码、员工「小朱」正确登录、会话刷新、普通员工访问管理页被拒、未登记端口和原回调被拒，以及恢复默认地址。
- Edge 联调验证管理员保存新地址、认证中心重启后配置保留、工单端切换到新回调后成功登录。页面升级后重新检查了桌面和 390 像素宽度的布局、400 与 403 提示、登录、退出和回调切换。
- 加入人事演示和员工管理后，再次用 Edge 检查首页、统一登录、工单、人事及两个管理页在桌面和 390 像素宽度下的布局。PowerShell 联调验证工单登录后可免输密码进入人事，人事会建立独立会话；在全新的浏览器会话中仍须登录。
- 在临时数据库中通过管理员表单登记财务。验证普通员工无法登记，格式不合法的回调被拒绝，刷新后登记记录仍在且明文密钥不再显示。用新凭据启动财务，验证授权码回跳后显示小朱。修改财务回调后，旧地址收到 `400`，更新财务端配置后能复用认证中心会话并成功登录，工单和人事的回调地址未变。
- 新版界面完成后，重新检查了首页、统一登录、应用配置和员工管理在桌面与 390 像素宽度下的显示。用浏览器验证小朱从工单登录后可以进入人事和财务，联调脚本复验了旧回调被拒和人事权限开关。另用临时数据库验证新版登记表单的错误提示、保存结果和密钥只展示一次。
- Compose 配置校验通过。本地模拟了浏览器地址和后端通信地址分离，工单后端成功通过内部地址换取凭证、读取公钥与用户信息。镜像构建和容器启动待在有 Docker Engine 的环境实测。

**财务接入复现步骤**

按 README 登记财务，使用生成的 ID 和密钥启动 `finance` 实例。在新会话验证财务可以完成授权码登录，在已有员工会话验证免输密码。刷新管理页，确认登记仍在，明文密钥已隐藏。最后修改财务回调，检查旧地址被拒、新地址放行，并核对工单和人事的回调配置。操作入口和命令见[登记并启动财务演示](../README.md#登记并启动财务演示)。
